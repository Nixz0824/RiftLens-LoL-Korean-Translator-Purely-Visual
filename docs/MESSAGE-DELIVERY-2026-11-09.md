# 消息时效与翻译完整性修复

日期：2026-11-09

## 行为

- 消息从稳定截图采集时开始计时，OCR、Vision、排队、聚合、文本翻译和 TTS 共用同一个预算。运行中的耗时使用 `TimeProvider` 的单调时钟，系统时间调整不会使消息续期。
- 当前初始预算：普通玩家聊天 6 秒、由现有紧急词规则识别的玩家聊天 4.5 秒、信号和系统消息 4 秒。它们是待真实回放验证的初始策略，不是已测得的延迟 SLA。
- 入队及消费时跳过过期消息。混合轮次先逐条剔除过期行，再保持原文、评估 ID 和翻译输入的对应关系。剩余轮次采用最早到期行的期限。
- 文本翻译和 Vision 请求不能超过剩余预算；晚于截止时间返回的结果也会被丢弃。暂停、停止和原有 HTTP 超时恢复逻辑继续生效。
- TTS 入队不重新计时。出队、合成前、合成完成及开始播放前都检查时效。合成的本地截止取消不会将语音供应商标记为离线。已经开始的音频允许完成，暂停/静音仍可中断。
- 同一玩家的聚合维持原有空闲等待和紧急立即输出路径，并增加从第一条开始的 2.5 秒最长等待。空闲等待及残行补等均不能超过这个上限。第八条不同内容到达时立即输出整轮，后续内容进入新轮次。
- 过期消息在进入翻译前会被跳过，不补做历史译文；已经到达界面但在等待 UI/TTS 时过期的结果可以留在历史中，禁止开始语音。

## 翻译协议

请求的 `chatLines` 改为 `{id, text}[]`，模型只返回：

```json
{
  "displayLines": [
    {"id": "line-1", "translation": "请上路支援。"},
    {"id": "line-2", "translation": "小心敌方打野。"}
  ],
  "toxicityFiltered": false
}
```

只接受 `finish_reason=stop`、一个 choice、正确字段类型及完整的逐行 ID 集合。每行必须非空并满足长度上限；重复、未知、缺失 ID 或额外行都会拒绝本轮。返回行顺序可不同，代码按输入 ID 恢复顺序。仅构建所需的字幕和过滤字段，模型返回的额外播报策略字段不会生效。

`max_tokens` 随原文长度和行数增加，范围为 384–4096。仍使用现有 `json_object` 模式，不要求供应商支持 JSON Schema。自定义兼容接口也必须遵守新的内容结构并提供正常完成状态，旧字符串数组不会作为已验证结果接受。校验失败会报告跳过原因，继续处理下一轮。

本地语音规划器额外检查行数。字幕较长、完整播报超过现有限额时保留全部文字并静音，避免截掉否定词、条件或目标。逐行 ID 只能证明配对完整，不能证明译文语义正确；现有语义规则和最终播报策略继续执行。
