# RiftLens 技术选型判断

日期：2026-11-09。目标是 Windows 游戏场景下的稳定启动、低干扰、准确识别、及时翻译与播报，以及可维护的界面。

## 结论

保留 C# 和现有 HTML/CSS/JavaScript 界面；近期独立升级 .NET 10 LTS。先解决当前 WebView2 启动路径问题，再用真实聊天回放测量 OCR、翻译与语音延迟。当前没有证据支持整体换语言或重写界面框架。

| 层次 | 当前选择 | 判断 | 依据与边界 |
|---|---|---|---|
| 主程序语言 | C# | 保留 | 已支持 Windows 截图、窗口管理、异步网络、语音、配置和本地推理。当前没有发现必须更换语言才能解决的限制。 |
| 运行时 | .NET 8 | 建议独立迁移 .NET 10 LTS | 微软官方支持元数据列明 .NET 8 于 2026-11-10 结束支持，.NET 10 LTS 到 2028-11-14。SDK 能编译不代表目标运行时已经升级。 |
| 桌面宿主 | WinForms + WebView2 | 先修复并保留 | 已有完整 UI 和原生功能。此次故障发生在 WebView2 控制器创建阶段；新项目内目录能渲染，AppData 路径下的旧目录和新目录均复现失败，不能简单归因于旧缓存损坏或语言性能。 |
| 界面实现 | HTML/CSS/JavaScript | 保留，继续细节优化 | 当前页面规模不需要为组件数量引入整个新框架。布局、反馈、键盘操作和状态同步可直接改善。 |
| OCR 推理 | PP-OCRv5 + ONNX Runtime | 保留基线，再测候选 | 重型计算已由原生推理库完成。仅把外层 C# 改成 C++ 或 Rust，并不会自动加速这些模型算子。 |
| Python | 字典、评估和数据工具 | 继续用于离线工具 | 适合数据处理与实验；没有必要将正常运行的桌面主程序整体改写为 Python。 |

## 哪些替换有条件成立

- **C++ / Rust**：只有在分析器证明自编写的截图、图像处理或数据搬运占据主要耗时，且现有 C# 实现已合理优化时，才值得将明确的热点做成小型原生模块。先替换热点，无须重写整个应用。
- **WPF / WinUI 3**：当 WebView2 在目标机器上仍持续出现无法恢复的兼容故障，或需要更深的原生辅助功能与系统整合时，可以制作同一页面的验证样机。它们不天然保证更低延迟；必须比较部署、DPI、键盘、资源占用与实际维护成本。
- **Avalonia**：需要跨平台时才有明确收益。当前仅面向 Windows，额外迁移成本没有对应的已确认需求。
- **Electron**：可以复用 Web UI，但仍引入 Chromium 宿主，并增加独立打包与更新职责；不能用它保证解决当前机器的所有浏览器存储问题。资源占用需要本机测量。
- **React / Vue**：当页面、交互状态和可复用组件数量显著增加时可以考虑。当前的表单、菜单和历史表可以在既有实现内维护，单纯切换框架不保证体验提高。

## 最能改善效果的顺序

1. 修复正式启动环境中的界面加载，确认用户看到真实首页；错误恢复应保留 API Key、应用设置和原目录。
2. 独立迁移 .NET 10，固定 SDK 和发布流程。验证 ONNX、Tesseract、NAudio、WebView2、DPI、托盘和退出；不同时改变 UI 框架。
3. 用固定真实聊天回放测量识别质量、端到端 P50/P95、过期比例、重复播报及资源占用。
4. 根据实测占比选择行级 OCR 复用、按需第二识别器、翻译请求预算或 TTS 首音频优化。模型升级也应使用同一回放集验证。
5. 只有现有方案达不到已定义目标时，再比较新的 UI 宿主或原生热点实现。

## 当前证据的限度

已有离线回归能证明已覆盖场景的行为，界面交互测试能证明操作与状态反馈；它们不能代替真实对局长测、在线模型质量评估或不同语言的同条件性能比较。目前没有这样的横向基准，因此不宣称某种语言、框架或模型是这个项目的“绝对最快/最好”。
